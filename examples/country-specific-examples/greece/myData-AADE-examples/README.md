# Greece myData/AADE Examples

This directory contains PUF example files demonstrating how to send Greek myDATA/AADE reporting data through the Ilyda Greece clearance flow. Each file demonstrates a specific myDATA scenario.

> **Note:** These examples cover the **data-fields** approach — myDATA/AADE content sent as structured `RestrictedInformation`/`RestrictedInformationLine`/`Classification` fields, from which the partner (Ilyda) builds the actual myDATA XML submission to AADE. This is a different, separate mechanism from the existing official example `puf-billing/examples/country-specific-examples/greece/PUF_Greece_Invoice.xml`, which demonstrates the **attachment** approach — a complete myDATA XML file generated by the customer and attached to the invoice (detected via `##InvoicesDoc##`/`MYDATA` description). Which mechanism a given customer uses is a per-trading-relationship decision; the two are not combined in a single document. See "Relationship to the attachment approach" below.

## Overview

Greek e-invoicing requires invoices to be cleared through AADE's myDATA platform before delivery to the buyer. These examples demonstrate key myDATA/AADE requirements including:

- Header-level myDATA identifiers: series, serial number (`aa`), invoice type code
- Payment method reporting (AADE payment code, distinct from the standard UBL payment means code)
- Document totals reported to AADE (net, VAT, gross)
- Line-level myDATA row detail: net amount, VAT amount, numeric AADE VAT category code
- AADE income/expense classification (`E3_xxx` codes), at both line and document level
- Numeric AADE VAT exemption cause codes, and when they are mandatory vs. forbidden
- Self-billing (`SelfBilled` extension) and its interaction with classification
- Correlated invoices for associated credit notes
- Multiple VAT rates, VAT exemption, and reverse charge/intra-community supply scenarios

All myDATA/AADE fields use Ilyda's own **ET-#** (field) / **EG-#** (group) numbering — these are not EN 16931 business terms, since myDATA/AADE reporting is a Greece-specific partner extension, not part of the European semantic data model. Standard EN 16931 fields in these examples are still annotated with their own BT/BG codes for comparison.

Every example in this directory has been run through the actual PUF-to-internal, Ilyda clearance-request, and Peppol BIS 3.0 transforms to confirm it produces valid, XSD-compliant output.

## Example Files

### 1. PUF_Generic_Sample_myData_AADE.xml

**Standard Sales/Service Invoice**

Demonstrates:

- myDATA invoice type 2.1 (Service Invoice)
- Two lines, both at the standard 24% VAT rate
- Header myDATA fields: series, `aa`, invoice type, payment method, document totals
- Line-level myDATA row detail with numeric VAT category and income classification
- Document-level classification summary

**Key Features:**

- Document type: 380
- All myDATA header keys sent already `myDATA_XML_`-prefixed (see "Sending the correct PUF key" below)
- Baseline example — other scenarios below build on this structure

---

### 2. PUF_Generic_Sample_myData_AADE_CreditNote.xml

**Credit Note — Non-Associated (myDATA type 5.2)**

Demonstrates:

- Credit note not linked to a specific original invoice (`correlatedInvoices` not sent)
- `CreditNote` PUF root (not `Invoice`) — a dedicated PUF profile, handled by the same generic PUF-to-internal transform
- A zero-value reference line (id 10) with no corresponding myDATA line-level entry, alongside a real credited line (id 20)
- No sign-flip: `CreditNoteTypeCode` carries no `@name="REFUNDNOTE"` attribute, so amounts stay positive

**Key Features:**

- Document type: 381
- Demonstrates that zero-value lines are excluded from myDATA row-level detail

---

### 3. PUF_Generic_Sample_myData_AADE_CreditNote_Associated.xml

**Credit Note — Associated (myDATA type 5.1)**

Demonstrates:

- Credit note explicitly linked to the original invoice via `myDATA_XML_correlatedInvoices`
- `cac:BillingReference` pointing back to the original invoice (`EXAMPLE-INV-0001`)
- Partial credit — the correlated invoice's full amount is not being credited

**Key Features:**

- Document type: 381
- Use alongside Example 2 to compare Associated (5.1) vs. Non-Associated (5.2) credit notes

---

### 4. PUF_Generic_Sample_myData_AADE_MultipleVATRates.xml

**Invoice with Multiple VAT Rates**

Demonstrates:

- Two lines at different VAT rates: 24% (numeric AADE category 1) and 13% (numeric AADE category 2)
- Two separate `cac:TaxSubtotal` entries in the header VAT breakdown, and two corresponding myDATA line-level VAT category entries
- Confirms the Ilyda clearance request correctly produces two `vatBreakdowns` entries, one per rate

**Key Features:**

- Document type: 380, myDATA invoice type 1.1 (Sales Invoice)
- Demonstrates that VAT category is genuinely a line-level (not document-level) concept

---

### 5. PUF_Generic_Sample_myData_AADE_VATExemption.xml

**VAT-Exempt Invoice**

Demonstrates:

- Line and header VAT category `E` (Exempt), numeric AADE VAT category 7 (Without VAT, 0%)
- Numeric AADE VAT exemption cause code 1 ("Without VAT - article 3 of the VAT code") at both the standard EN 16931 field (BT-121) and the myDATA-specific line-level field
- The exemption cause code is **mandatory whenever the AADE VAT category is 7** (AADE error 217), and **only applicable when it is 7** (AADE error 271) — do not send it for any other category value

**Key Features:**

- Document type: 380, myDATA invoice type 1.1
- Confirms `categoryCode: "E"` and `exemptionReasonCode`/`exemptionReasonText` flow correctly into the header-level `vatBreakdowns` entry

---

### 6. PUF_Generic_Sample_myData_AADE_ReverseCharge.xml

**Reverse Charge / Intra-Community Supply**

Demonstrates:

- Standard VAT category `AE` (Reverse Charge), numeric AADE VAT category 7
- Buyer registered in another EU member state (Germany)
- Numeric AADE VAT exemption cause code 14 ("Without VAT - article 28 of the VAT Code" — intra-community supply of goods), same mandatory-when-category-7 rule as the VAT exemption example
- Confirms `vatPaidByBuyer` (EL-BT-2) resolves to `true`

**Key Features:**

- Document type: 380, myDATA invoice type 1.2 (Sales Invoice / Intra-community Supplies)
- Same exemption-cause-code mechanism as Example 5, different underlying business scenario (reverse charge, not a literal exemption)

---

### 7. PUF_Generic_Sample_myData_AADE_SelfBilling.xml

**Self-Billed Invoice**

Demonstrates:

- `PageroExtension:SelfBilled` — a dedicated PUF extension, separate from the myDATA `RestrictedInformation` block, set to `true`
- Self-pricing (myDATA EL-BT-1) applies only to a subset of AADE invoice types (this example uses 1.1, which is in that subset)
- AADE **forbids** income/expense classification on self-billed documents — neither the line-level `puf:Classification` nor the document-level classification summary extension is sent

**Key Features:**

- Document type: 380, myDATA invoice type 1.1
- Confirms `incomeClassifications: null` in the Ilyda clearance request output — no classification data is forwarded, by design

## myDATA/AADE Extension Groups

| Group | Description | Examples |
|---|---|---|
| EL-BG-1 | Header data: series, `aa`, invoice type code | All |
| EL-BG-4 | Document totals: net value, VAT amount, gross value | All |
| EL-BG-5 | Payment method: AADE payment code and amount | All |
| EL-BT-1 | Self-pricing (self-billed flag) | 7 |
| EL-BT-38 / EL-BT-52 | Income/expense classification | 1–6 (omitted in 7) |
| EL-BT-39 | Line-level myDATA row detail | All |

## Invoice Type Codes Used

| myDATA type | Description | Examples |
|---|---|---|
| 1.1 | Sales Invoice | 4, 5, 7 |
| 1.2 | Sales Invoice / Intra-community Supplies | 6 |
| 2.1 | Service Invoice | 1 |
| 5.1 | Credit Invoice / Associated | 3 |
| 5.2 | Credit Invoice / Non-Associated | 2 |

Full invoice type catalogue: AADE myDATA API Documentation, section 8.1.

## AADE VAT Category Codes (numeric, section 8.2)

| Code | Rate/meaning | Examples |
|---|---|---|
| 1 | 24% | 1, 4 |
| 2 | 13% | 4 |
| 7 | Without VAT (0%) | 5, 6 |
| 8 | Records without VAT (e.g. payroll, amortisations) | — |
| 9 / 10 | 3% / 4% (art. 31 ν.5057/2023) | — |

Which of these are even legal is invoice-type-dependent, not universal — some invoice types restrict this field to only 7 or 8 (AADE error 215), others forbid both 7 and 8 (error 234), and some forbid 8 alone (error 216). Check the target invoice type's own allowed-category rule before reusing a category from a different invoice type's example.

## AADE VAT Exemption Cause Codes Used (section 8.3)

| Code | Meaning | Examples |
|---|---|---|
| 1 | Without VAT - article 3 of the VAT code | 5 |
| 14 | Without VAT - article 28 of the VAT Code (intra-community supply of goods) | 6 |

Mandatory whenever the line's AADE VAT category is 7 (error 217); only applicable when it is 7 (error 271).

## Key RestrictedInformation Keys

| Key | Description | Level | Examples |
|---|---|---|---|
| `myDATA_XML_series` | Invoice series (EL-BT-30) | Document | All |
| `myDATA_XML_aa` | Invoice serial number (EL-BT-31) | Document | All |
| `myDATA_XML_invoiceType` | AADE invoice type code (EL-BT-8) | Document | All |
| `myDATA_XML_paymentType_1` / `myDATA_XML_paymentAmount_1` | AADE payment method code/amount, first payment method only (EL-BT-63/EL-BT-65) | Document | All |
| `myDATA_XML_totalNetValue` / `myDATA_XML_totalVatAmount` / `myDATA_XML_totalGrossValue` | Document totals (EL-BT-46/EL-BT-47/EL-BT-25) | Document | All |
| `myDATA_XML_correlatedInvoices` | Original invoice's myDATA serial number(s), for Associated (5.1) credit notes only | Document | 3 |
| `myDATA_XML` (RestrictedInformationLine key) | Line-level myDATA row detail (EL-BT-39) | Line | All |

`SelfBilled` (Example 7) is sent via its own extension URI (`PageroExtension:SelfBilled`), not a `RestrictedInformation` key.

## Relationship to the Attachment Approach

`PUF_Greece_Invoice.xml` in the parent `greece` folder demonstrates the alternative **myDataAttachment** mechanism: a complete myDATA XML file, generated by the customer's own system, attached with `DocumentDescription` set to `##InvoicesDoc##`. In that approach, Ilyda takes the attached file largely as-is; none of the `RestrictedInformation`/`RestrictedInformationLine`/`Classification` fields shown in this directory's examples are needed. The two mechanisms are not combined on a single document — a given trading relationship uses one or the other.
