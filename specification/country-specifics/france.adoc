This section contains information about requirements and other information concerning invoicing in France.

==== French E-Invoicing Mandate (2026)

France implemented a mandatory B2B/B2G e-invoicing system starting in 2026, requiring all invoices between French entities to be transmitted through certified platforms (Plateformes Agréées - PA).

==== French Text Codes (Note Elements)

France requires specific information to be provided in invoice notes using standardized text code prefixes. These text codes identify the type of legal, regulatory, or commercial information being provided.

===== Text Code Format

Each text code must be provided in a separate `cbc:Note` element with the format: `#CODE#value`

NOTE: `cbc:Note` is typed as `NoteType`, which extends a bare text type and has no note-code component. The subject code is therefore not carried as a code of its own, and the `#CODE#` prefix is a text convention inside the note text that neither the PUF schema nor PUF validation can check. The prefix is split into the subject code (BT-21) and the note text (BT-22) when the document is transformed to the French target format.

|*Required:* `MEMBRE_ASSUJETTI_UNIQUE`
|===

IMPORTANT:

* The #PMT# fixed indemnity amount is legally set at €40.00 per Article L441-10 of the French Commercial Code
* #BAR# is mandatory for every non-B2G France scenario and must contain exactly ONE of the specified values: `B2B` (e-invoicing), `B2BINT` (B2B international e-reporting), `B2C` (B2C e-reporting), `B2CINT` (B2C international e-reporting), `OUTOFSCOPE` (outside reform scope), or `ARCHIVEONLY` (internal credit note, see <<_archive_only_credit_notes_archiveonly, Archive-only credit notes>>).
* #BAR# is not required for B2G. B2G examples use `#ADN#B2G` and should provide `puf:ComplianceActivatedIndicator` = `true`
* Only ONE #BAR# note is allowed per invoice
* `#REG#` can be used for seller registration data such as share capital and other regulatory company information
* `#TXD#` must carry the literal value `MEMBRE_ASSUJETTI_UNIQUE`. The French phrase `Membre d'un assujetti unique` is the value BR-FR-MAP-06 and BR-FR-MAP-07 require in the downstream Flux 1 note text (BT-22) and Flux 10.1 report note (TT-27), and is never what a source document carries
* The `#TXD#` note must be the last `cbc:Note` of the document, or the note that follows it must itself begin with a text code prefix. `BR-FR-CO-14` joins all document-level notes into one string with no separator and reads the value between the TXD prefix and the next hash character, so a following note without a text code prefix is absorbed into that value and the fatal rule fires

==== Compliance and Regulated Status (Type de processus métier)

Every French invoice / credit note is either *regulated* — processed *within* the French e-invoicing reform, with Pagero acting as the accredited platform (PA) and applying the stricter compliance checks and validations the reform requires — or *non-regulated*, processed *outside* that regime (for example B2C or cross-border documents). This corresponds to the *Type de processus métier* concept (MDG-2).

The status is conveyed to Pagero Online in one of two ways:

Explicit indicator (authoritative)::
Set `puf:ComplianceExtension/puf:ComplianceActivatedIndicator` (see <<_compliance_extension>>) to `true` for *REGULATED* or `false` for *NON_REGULATED*. When present, this value takes precedence.

`#BAR#` treatment-type note (non-B2G fallback)::
For non-B2G documents, when the explicit indicator is absent, Pagero Online derives the status from the mandatory `#BAR#` note (see <<_french_text_codes_note_elements, French Text Codes>>): `#BAR#B2B` is treated as *REGULATED*; every other treatment type (`B2BINT`, `B2C`, `B2CINT`, `OUTOFSCOPE`, `ARCHIVEONLY`) is treated as *NON_REGULATED*.

B2G classification::
For B2G, `#BAR#` is not required. `#ADN#B2G` is the invoice-level B2G indicator used by the Chorus Pro qualification examples. Pagero senders should also set `puf:ComplianceActivatedIndicator` to `true`; channel or directory context may independently identify the transaction as B2G.

[IMPORTANT]
====
Declaring the regulated / non-regulated status is the *sender's responsibility*. The `#BAR#`-derived value is a best-effort fallback, provided for convenience only. If the sender does not supply the status explicitly and the fallback resolves it incorrectly, the sender remains responsible — the status should have been provided in the first place, ideally via `puf:ComplianceActivatedIndicator`.
====

*Example — explicitly marking an invoice as regulated*
[source,xml]
----
<Invoice>
    <!-- Code omitted for clarity -->
    <ext:UBLExtensions>
        <ext:UBLExtension>
            <ext:ExtensionURI>urn:pagero:ExtensionComponent:1.0:PageroExtension:ComplianceExtension</ext:ExtensionURI>
            <ext:ExtensionContent>
                <puf:PageroExtension>
                    <puf:ComplianceExtension>
                        <puf:ComplianceActivatedIndicator>true</puf:ComplianceActivatedIndicator>
                    </puf:ComplianceExtension>
                </puf:PageroExtension>
            </ext:ExtensionContent>
        </ext:UBLExtension>
    </ext:UBLExtensions>
    <!-- Equivalent fallback when the explicit indicator is omitted: <cbc:Note>#BAR#B2B</cbc:Note> -->
    <!-- Code omitted for clarity -->
</Invoice>
----

==== Archive-only credit notes (ARCHIVEONLY)

`#BAR#ARCHIVEONLY` marks an *internal credit note* (AVOIR interne) reversing an invoice that was
*Rejetée* or *Refusée*, submitted for archiving only. Per AFNOR XP Z12-012 rule BR-FR-20 such a
document must not be subject to e-invoicing processing: no flux 1 and no transmission to the recipient.
Pagero Online will neither clear it nor deliver it, so it never reaches the buyer.

Send it as a credit note and reference the reversed invoice in BG-3, which is what XP Z12-014 §2.2
scopes the behaviour to. Do not add `puf:ExternalDeliveryType`; it is not needed for this case.

*Example — archive-only credit note*
[source,xml]
----
<CreditNote>
    <!-- Code omitted for clarity -->
    <cbc:CreditNoteTypeCode name="B1">381</cbc:CreditNoteTypeCode>
    <cbc:Note>#BAR#ARCHIVEONLY</cbc:Note>

    <!-- BG-3 reference to the reversed invoice -->
    <cac:BillingReference>
        <cac:InvoiceDocumentReference>
            <cbc:ID>INV-2026-000123</cbc:ID>
            <cbc:IssueDate>2026-09-01</cbc:IssueDate>
        </cac:InvoiceDocumentReference>
    </cac:BillingReference>
    <!-- Code omitted for clarity -->
</CreditNote>
----

==== Credit note for global discount (Code 262)

Invoice type code `262` ("Avoir pour Remise Globale") is used for credit notes
issued against one or more previously sent invoices to apply a global
discount or rebate (commercial gesture, end-of-year volume rebate, etc.).

When using code `262`, the following PUF fields are conditionally mandatory:

* **BT-12** (Contract reference) — `cac:ContractDocumentReference/cbc:ID`
* **BG-14** (Invoice period) — `cac:InvoicePeriod/cbc:StartDate` and
  `cac:InvoicePeriod/cbc:EndDate`

The PUF document itself carries `cbc:CreditNoteTypeCode>262`. Downstream
transformation to the French target formats is flux-specific:

* **Flux 1** (clearance / subset to PPF) and **Flux 10.1** (e-reporting):
  the value is remapped to `381` and the BT-12 / BT-73 values are carried
  into the preceding-invoice reference (BT-25 / BT-26).
* **Flux 2** (invoice transmission): the value is preserved as `262` and
  BT-12 / BT-73 remain in their normal locations.

*Example*
[source,xml]
----
<CreditNote>
    <!-- Code omitted for clarity -->
    <cbc:CreditNoteTypeCode name="B1">262</cbc:CreditNoteTypeCode>
    <cac:InvoicePeriod>
        <cbc:StartDate>2026-01-01</cbc:StartDate>
        <cbc:EndDate>2026-03-31</cbc:EndDate>
    </cac:InvoicePeriod>
    <cac:ContractDocumentReference>
        <cbc:ID>CONTRACT-2026-001</cbc:ID>
    </cac:ContractDocumentReference>
    <!-- Code omitted for clarity -->
</CreditNote>

==== Sub-lines and Line Groupings

France (EXTENDED-CTC-FR profile) supports hierarchical invoice lines - sub-lines and line groupings - for composite articles (kits, packs), multi-VAT-rate products, and parent lines with supplements. The lines stay flat; the hierarchy is carried by the generic <<line-sublines, Sub-lines extension>> (`puf:RowType` + `puf:ParentLineID`) together with the native `cac:Item/cbc:PackQuantity`.

These map to the French line-grouping extensions as follows:

[cols="2,2,3", options="header"]
|===
|PUF |France (EXTENDED-CTC-FR) |Description

|`puf:RowType` = `SUMMARY` / `PLAIN` / `INFO`
|EXT-FR-FE-163 line subtype = `GROUP` / `DETAIL` / `INFORMATION`
|Qualifies the line as a grouping/subtotal line, a detail line, or an informational line.

|`puf:ParentLineID`
|EXT-FR-FE-162 parent line identifier
|The `cbc:ID` (BT-126) of the parent line. A `GROUP` may reference another `GROUP`, so multi-level nesting is supported.

|`cac:Item/cbc:PackQuantity`
|EXT-FR-FE-191 quantity per parent unit
|Quantity of the sub-line article contained in one unit of the parent line.
|===

IMPORTANT:

* Only `DETAIL` and standard lines participate in the document totals (BT-106/BT-109) and the VAT breakdown (BG-23). `GROUP` and `INFORMATION` lines are excluded (XP Z12-014 §3.2.37).
* If a `GROUP` line carries BT-131 (line net amount), it must equal the sum of BT-131 of its direct `DETAIL`/`GROUP` children.
* `GROUP` and `INFORMATION` lines are kept in the commercial invoice (Flux 2) but dropped from the clearance (Flux 1) and e-reporting (Flux 10) transmissions, which carry only `DETAIL` and standard lines.
* Sub-lines do not require a specific business process code; the standard B/S/M codes apply.

*Example - group line with detail sub-line*
[source,xml]
----
<Invoice>
    <!-- Code omitted for clarity -->
    <!-- Group line: subtotal of its children, excluded from totals -->
    <cac:InvoiceLine>
        <ext:UBLExtensions>
            <ext:UBLExtension>
                <ext:ExtensionURI>urn:pagero:ExtensionComponent:1.0:PageroExtension:LineExtension</ext:ExtensionURI>
                <ext:ExtensionContent>
                    <puf:PageroExtension>
                        <puf:LineExtension>
                            <puf:RowType>SUMMARY</puf:RowType><!--1-->
                        </puf:LineExtension>
                    </puf:PageroExtension>
                </ext:ExtensionContent>
            </ext:UBLExtension>
        </ext:UBLExtensions>
        <cbc:ID>10</cbc:ID>
        <cbc:LineExtensionAmount currencyID="EUR">1000.00</cbc:LineExtensionAmount>
        <!-- Code omitted for clarity -->
    </cac:InvoiceLine>
    <!-- Detail line: parent 10, with quantity per parent unit -->
    <cac:InvoiceLine>
        <ext:UBLExtensions>
            <ext:UBLExtension>
                <ext:ExtensionURI>urn:pagero:ExtensionComponent:1.0:PageroExtension:LineExtension</ext:ExtensionURI>
                <ext:ExtensionContent>
                    <puf:PageroExtension>
                        <puf:LineExtension>
                            <puf:RowType>PLAIN</puf:RowType><!--2-->

        <cbc:ID>20</cbc:ID>

        <cac:Item>
            <cbc:PackQuantity unitCode="H87">6</cbc:PackQuantity><!--4-->
            <cbc:Name>Component</cbc:Name>

<3> `ParentLineID` -> EXT-FR-FE-162: references the group line `cbc:ID`.

==== Business and VAT Identification

France uses SIRET (14-digit) and SIREN (9-digit) numbers for business identification.

===== Endpoint Identification

For electronic addressing in the French e-invoicing system, **schemeID 0225** is the primary electronic addressing scheme. The endpoint value can contain composite information combining SIREN, SIRET, and optional routing identifiers.

**Endpoint Registration Formats (schemeID 0225):**

There are four possible registration formats in the French e-invoicing directory (annuaire):

1. `SIREN` - Company identifier only
2. `SIREN_SUFFIX` - Company identifier with custom suffix
3. `SIREN_SIRET` - Company and establishment identifiers
4. `SIREN_SIRET_CODEROUTAGE` - Full identifier with routing code

Where:

* **SIREN** (schemeID 0002) - 9-digit company identifier
* **SIRET** (schemeID 0009) - 14-digit establishment identifier
* **SUFFIX** - Custom suffix appended directly to SIREN (no separate scheme code)
* **CODE ROUTAGE** (schemeID 0224) - Buyer-defined routing code for internal distribution (e.g., department, cost center, or business unit)

NOTE: SUFFIX and CODE ROUTAGE achieve similar functionality at different organizational levels. Both are entirely determined by the buyer for routing invoices to the appropriate internal recipient. The platform must register such addresses in the French e-invoicing registry.

**Party Structure Requirements:**

In addition to the endpoint (schemeID 0225), the individual identifier components should be provided in the party structure:

* **SIREN** → `PartyLegalEntity/CompanyID` with schemeID `0002`
* **SIRET** → `PartyIdentification/ID` with schemeID `0009`
* **CODE ROUTAGE** → `PartyIdentification/ID` with schemeID `0224` (when applicable)

===== Single Taxable Person Identification (Assujetti Unique)

Identification scheme `0231` carries the SIREN of the single taxable person (assujetti unique) that the seller is a member of. It identifies a legal entity other than the seller, and it is valid only as a seller private identifier (BT-29):

* Provide it on `cac:AccountingSupplierParty/cac:Party/cac:PartyIdentification/cbc:ID` with `@schemeID` `0231`. Scheme `0231` must never be used on the buyer, on any other party, or on `cac:PartyLegalEntity/cbc:CompanyID`.
* Provide it exactly once. Only one identifier per scheme is allowed for a party (`BR-FR-CO-10`).
* The value must be exactly 9 digits (`BR-FR-32`).
* `0231` is an ISO 6523 ICD value and not a CEF EAS value, so it must never be used as an electronic address in `cbc:EndpointID` (BT-34 and BT-49), which would breach `BR-CL-25`.
* The value must be the SIREN of a single taxable person registered in the PPF Annuaire (`BR-FR-CO-13`). This is a business rule verified by the PPF, with no Schematron implementation, and senders cannot pre-check it: the Annuaire data model has no representation of a single taxable person.
* `cac:PartyLegalEntity/cbc:CompanyID` with scheme `0002` is unaffected and remains the seller's own SIREN (BT-30).

Using scheme `0231` obliges the sender to provide two further elements in the same document:

* The note `#TXD#MEMBRE_ASSUJETTI_UNIQUE` (`BR-FR-CO-14`), see <<_french_text_codes_note_elements, French Text Codes>>. Place it as the last `cbc:Note` of the document, or immediately before another note that begins with a text code prefix. `BR-FR-CO-14` joins all document-level notes into one string with no separator and reads the value between the TXD prefix and the next hash character, so a following note without a text code prefix is absorbed into that value and the fatal rule fires.
* A `cac:TaxRepresentativeParty` (BG-11) carrying the name, VAT number (BT-63) and postal address of the single taxable person (`BR-FR-CO-15`). The VAT for the invoice is declared by the single taxable person, not by the seller.

            </cac:PartyIdentification>
            <cac:PartyIdentification>
                <cbc:ID schemeID="0231">888999000</cbc:ID><!--4-->

==== Service code

Service code is a routing code required by some customers to identify the correct recipient in French Government Portal.

It's used as an addition to the https://en.m.wikipedia.org/wiki/SIRET_code[SIRET number^], which is the main identifier for all government recipients.

The Service code should be provided in the extension block under <<_cacaccountingcustomerparty, cac:AccountingCustomerParty/cac:Party>>, in the structure `puf:PageroExtension/puf:PartyExtension/puf:ADAID`.

More information how to use ADAID can be found <<_additional_destination_address_identifier_adaid, here>>.

See example below, note that `cbc:Name` is not mandatory to send, but opens up the possibility to provide the name of the receiving unit.

*Example*
[source,xml]
----
<Invoice>
    <!-- Code omitted for clarity -->
    <cac:AccountingCustomerParty>
        <!-- Code omitted for clarity -->
        <cac:Party>
            <ext:UBLExtensions>
                <ext:UBLExtension>
                    <ext:ExtensionURI>urn:pagero:ExtensionComponent:1.0:PageroExtension:PartyExtension</ext:ExtensionURI>
                    <ext:ExtensionContent>
                        <puf:PageroExtension>
                            <puf:PartyExtension>
                                <puf:ADAID>
                                    <cbc:ID>1234567890</cbc:ID>
                                    <cbc:Name>Name of receiving unit</cbc:Name>
                                    <puf:IDType listID="PUF-002-ADAID">FR:ServiceCode</puf:IDType>
                                </puf:ADAID>
                            </puf:PartyExtension>
                        </puf:PageroExtension>
                    </ext:ExtensionContent>
                </ext:UBLExtension>
            </ext:UBLExtensions>
            <!-- Code omitted for clarity -->
        </cac:Party>
    </cac:AccountingCustomerParty>
    <!-- Code omitted for clarity -->
</Invoice>

==== B2G / public sector (Chorus Pro)

French B2G invoices are subject to the additional `BR-FR-CPRO` rules. The rules are activated when the transaction is identified as B2G through `#ADN#B2G`, channel context, or public-buyer directory information.

Key requirements include:

* Seller private identifier (BT-29) and public buyer SIRET (BT-46) according to `BR-FR-CPRO-03`, `BR-FR-CPRO-09`, and `BR-FR-CPRO-10`.
* Buyer service code in BT-46 with scheme `0224` when required by the public buyer's directory configuration (`BR-FR-CPRO-11`).
* Commitment number (BT-13) when required by the public buyer's directory configuration (`BR-FR-CPRO-12` and `BR-FR-CPRO-13`).
* Seller Agent details for B2G subcontracting framework `S3` (`BR-FR-CPRO-21` and `BR-FR-CPRO-23`). This differs from private-market subcontracting framework `S5`, which uses the Payer block.
* Chorus Pro-specific cardinality and length constraints from the remaining `BR-FR-CPRO` rules.

The AIFE qualification `0225` endpoints shown in the B2G example files are test values. They must not be treated as a general rule for constructing production electronic addresses.

The following PUF files correspond to the eight AIFE invoice scenarios:

* `PUF_France_B2G_Simple_Invoice.xml`
* `PUF_France_B2G_CreditNote.xml`
* `PUF_France_B2G_UC1_MultiOrder_MultiDelivery_Invoice.xml`
* `PUF_France_B2G_UC7_PurchasingCard_Invoice.xml`
* `PUF_France_B2G_UC13_Subcontracting_DirectPayment_Invoice.xml`
* `PUF_France_B2G_UC17a_PaymentIntermediary_Invoice.xml`
* `PUF_France_B2G_UC20_PrepaymentInvoice.xml`
* `PUF_France_B2G_UC29_SingleVATEntity_Invoice.xml`
