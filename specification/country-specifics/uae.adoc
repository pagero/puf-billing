This section contains information about special requirements concerning invoicing in the United Arab Emirates (UAE).

PUF supports UAE billing through a combination of standard PUF elements and the existing PUF UBL extensions originally introduced for KSA.

==== Invoice type code and transaction type

Available invoice type code values to be used in the UAE can be found here: https://pagero.github.io/puf-code-lists/#_invoice_type_codes_united_arab_emirates[Invoice type codes United Arab Emirates^].

In addition to the type code, every UAE invoice MUST carry an *invoice transaction type code* (BTAE-02). The value is a fixed 8-character string of `0` and `1` flags identifying which UAE business contexts apply, provided as the `name` attribute on `cbc:InvoiceTypeCode` (or `cbc:CreditNoteTypeCode` for credit notes).

The position-by-position structure is documented here: https://pagero.github.io/puf-code-lists/#_invoice_transaction_type_code_united_arab_emirates[Invoice transaction type code United Arab Emirates^].

*Example* +
_Standard tax invoice in UAE without any of the special transaction contexts_
[source,xml]
----
<Invoice>
  <!-- Code omitted for clarity -->
  <cbc:InvoiceTypeCode name="00000000">380</cbc:InvoiceTypeCode><!--1-->
  <!-- Code omitted for clarity -->
</Invoice>
----
<1> InvoiceTypeCode `380` for "Tax Invoice". Attribute `name` carries the UAE invoice transaction type code (BTAE-02).

*Example* +
_Free-trade-zone invoice (FTZ flag in position 1)_
[source,xml]
----
<Invoice>
  <!-- Code omitted for clarity -->
  <cbc:InvoiceTypeCode name="10000000">380</cbc:InvoiceTypeCode><!--1-->
  <!-- Code omitted for clarity -->
</Invoice>
----
<1> Position 1 = `1` indicates Free Trade Zone supply.

==== Party identification

The UAE Tax Registration Number (TRN) is provided as the VAT identifier on `cac:PartyTaxScheme/cbc:CompanyID` with the tax scheme code `VAT`. The TRN is 15 alphanumeric characters, starts with `1` and ends with `03` (e.g. `100000000000003`).

The TRN may alternatively be carried on `cac:PartyIdentification/cbc:ID` with `@schemeID = 'AE:TRN'`. Use that form for a party that has no VAT accounting role in the document and therefore no `cac:PartyTaxScheme` — in particular the free-trade-zone Beneficiary and the disclosed-agent Principle described below. Both forms resolve to the same TRN; when both are present on one party, `cac:PartyTaxScheme/cbc:CompanyID` takes precedence. A UAE identifier given on `cac:PartyIdentification/cbc:ID` *without* a scheme identifier is not processed.

When the supplier is not VAT-registered, the Tax Identification Number (TIN) is provided instead under `cac:PartyIdentification/cbc:ID` with `@schemeID = 'AE:TIN'`. The TIN is 10 numeric digits starting with `1` (e.g. `1000000000`) and, for a VAT-registered party, is the first 10 digits of the TRN.

*Example* +
_Seller TRN_
[source,xml]
----
<Invoice>
  <!-- Code omitted for clarity -->
  <cac:AccountingSupplierParty>
    <cac:Party>
      <!-- Code omitted for clarity -->
      <cac:PartyTaxScheme>
        <cbc:CompanyID>100000000000003</cbc:CompanyID><!--1-->
        <cac:TaxScheme>
          <cbc:ID>VAT</cbc:ID>
        </cac:TaxScheme>
      </cac:PartyTaxScheme>
      <!-- Code omitted for clarity -->
    </cac:Party>
  </cac:AccountingSupplierParty>
</Invoice>
----
<1> UAE TRN provided in `cac:PartyTaxScheme/cbc:CompanyID` with `cac:TaxScheme/cbc:ID = 'VAT'`.

==== Electronic address (Participant Identifier)

The seller and buyer electronic address (IBT-034 / IBT-049) is the Peppol *Participant Identifier* issued by the FTA. It MUST be the *10-digit TIN* under the Peppol EAS scheme `0235`.

The TIN is the first 10 digits of the 15-character TRN. The full TRN MUST NOT be used as the electronic address — it belongs on `cac:PartyTaxScheme/cbc:CompanyID` (IBT-031 / IBT-048) only.

[IMPORTANT]
====
The PUF-008 scheme code `AE:TIN` applies to `cac:PartyIdentification/cbc:ID`. It is *not* an endpoint scheme — `cbc:EndpointID/@schemeID` always carries the Peppol EAS code `0235`.
====

*Example* +
_Seller with TRN `100000000000003` and the derived Participant Identifier_
[source,xml]
----
<Invoice>
  <!-- Code omitted for clarity -->
  <cac:AccountingSupplierParty>
    <cac:Party>
      <cbc:EndpointID schemeID="0235">1000000000</cbc:EndpointID><!--1-->
      <!-- Code omitted for clarity -->
      <cac:PartyTaxScheme>
        <cbc:CompanyID>100000000000003</cbc:CompanyID><!--2-->
        <cac:TaxScheme>
          <cbc:ID>VAT</cbc:ID>
        </cac:TaxScheme>
      </cac:PartyTaxScheme>
    </cac:Party>
  </cac:AccountingSupplierParty>
</Invoice>
----
<1> Participant Identifier: scheme `0235` with the 10-digit TIN (the first 10 digits of the TRN).
<2> The full 15-character TRN stays on `cac:PartyTaxScheme/cbc:CompanyID`.

A party that is within scope of UAE e-invoicing but not registered for VAT has no TRN. It still has a TIN, obtained by registering with the FTA, and uses that TIN as its Participant Identifier.

Pagero sets the three predefined buyer endpoints under scheme `0235` itself, so they do not need to be sent: `9900000097` on a deemed supply, `9900000099` on an export to a buyer that is not reached over Peppol, and `9900000098` when a UAE buyer has no Participant Identifier on a document that is not an export. `9900000098` means that the buyer has not yet implemented Electronic Invoicing, and the supplier must then also issue a regular tax invoice, for example a PDF (UAE Electronic Invoicing Guidelines V1.1, p.23). A document with a predefined endpoint is reported to the FTA and is not exchanged over Peppol.

==== Legal registration identifier

PINT AE requires the seller's legal registration identifier on every document (ibr-150-ae) and the buyer's on a document of type `480` or `81` (ibr-136-ae). PUF carries this through `cac:PartyLegalEntity/cbc:CompanyID` with the registration type expressed via the standard `@schemeID` attribute. PUF does not use the PINT-AE `@schemeAgencyID` / `@schemeAgencyName` syntax — every UAE identifier flavour has its own PUF-008 scheme code.

The four primary types — Trade license, Emirates ID, Passport and Cabinet Decision — and the two supplementary identifiers (Legal Registration Authority, Passport issuing country) are documented here: https://pagero.github.io/puf-code-lists/#_identification_scheme_united_arab_emirates[Identification scheme United Arab Emirates^].

*Example* +
_Seller registered under a Trade License issued by the Department of Economic Development - Dubai_
[source,xml]
----
<Invoice>
  <!-- Code omitted for clarity -->
  <cac:AccountingSupplierParty>
    <cac:Party>
      <!-- Code omitted for clarity -->
      <cac:PartyIdentification>
        <cbc:ID schemeID="AE:LRA">Department of Economic Development - Dubai</cbc:ID><!--2-->
      </cac:PartyIdentification>
      <cac:PartyLegalEntity>
        <cbc:RegistrationName>Acme Trading LLC</cbc:RegistrationName>
        <cbc:CompanyID schemeID="AE:TL">CN-1234567</cbc:CompanyID><!--1-->
      </cac:PartyLegalEntity>
    </cac:Party>
  </cac:AccountingSupplierParty>
</Invoice>
----
<1> Trade license number on `cac:PartyLegalEntity/cbc:CompanyID` with `schemeID="AE:TL"`.
<2> Issuing authority (BTAE-12) carried as a separate `cac:PartyIdentification` entry with `schemeID="AE:LRA"`.

==== Country subdivision (Emirates)

Whenever a UAE address is provided (seller, buyer, delivery, tax representative), the country subdivision MUST be one of the seven Emirate codes:

[%autowidth]
|===
|Code |Emirate

|`AUH` |Abu Dhabi
|`DXB` |Dubai
|`SHJ` |Sharjah
|`UAQ` |Umm Al Quwain
|`FUJ` |Fujairah
|`AJM` |Ajman
|`RAK` |Ras Al Khaimah
|===

The Emirate code is provided in `cbc:CountrySubentity` and the country code in `cac:Country/cbc:IdentificationCode = 'AE'`.

The country subdivision itself is mandatory in every seller and buyer address, whatever the country (ibr-143-ae, ibr-144-ae), and in every delivery address that is provided. For an address outside the UAE, give the region, state or province.

==== Currency and AED amounts

The document currency code MUST be present (`cbc:DocumentCurrencyCode`). If the document currency is not AED, the tax accounting currency MUST be set to `AED` (`cbc:TaxCurrencyCode = 'AED'`) and the currency exchange rate MUST be provided.

When the document currency is not AED, the following amounts MUST be additionally expressed in AED through the standard PUF extensions:

[%autowidth.stretch]
|===
|Field |BT code |PUF extension

|Tax category tax amount in AED (per VAT breakdown) |IBT-190 |`puf:TaxSubtotalExtension/puf:TaxCurrencyTaxAmount[@currencyID = 'AED']`
|Invoice line VAT amount in AED |BTAE-08 |Second `cac:TaxTotal/cbc:TaxAmount[@currencyID = 'AED']` on the line
|Invoice line amount with VAT in AED |BTAE-10 |`puf:LineExtension/puf:TaxCurrencyTaxInclusiveLineExtensionAmount[@currencyID = 'AED']`
|Invoice (or CreditNote) total amount with VAT in AED |BTAE-20 |`puf:LegalMonetaryTotalExtension/puf:TaxCurrencyTaxInclusiveAmount[@currencyID = 'AED']`
|===

==== Item type, classification and Service Accounting Code

Every UAE invoice line MUST declare whether the item is goods, a service, or both, via the *item type* (BTAE-13). It is provided through `cac:CommodityClassification/cbc:CommodityCode`:

[%autowidth]
|===
|Code |Meaning

|`G` |Goods
|`S` |Services
|`B` |Both (goods and services on the same line)
|===

The item type drives two further requirements:

* When item type is `G` (or `B`), the *item classification* (IBT-158) MUST be present and the classification scheme identifier (`@listID`) MUST be `HS` (Harmonised Commodity Description and Coding System).
* When item type is `S` (or `B`), the *Service Accounting Code* (BTAE-17) MUST be present using `cac:AdditionalItemIdentification` with `@schemeID = 'SAC'`.

NOTE: The PINT-AE syntax table shows `cbc:ItemClassificationCode` as 1..1 within `cac:CommodityClassification`, but the validation artefacts do not enforce this: `ibr-184-ae` requires the item classification only when the item type is `G` (or `B`), and `ibr-188-ae` constrains the scheme identifier only when a classification is actually present. A pure service line therefore carries `cbc:CommodityCode` alone and is classified by its Service Accounting Code (BTAE-17). Do not invent an HS code for a service — HS classifies goods, and a placeholder value would misreport the supply.

*Example* +
_Line for a service, carrying the item type and the SAC code_
[source,xml]
----
<cac:InvoiceLine>
  <!-- Code omitted for clarity -->
  <cac:Item>
    <cbc:Description>Q1 advisory engagement</cbc:Description>
    <cbc:Name>Consulting services</cbc:Name>
    <cac:AdditionalItemIdentification>
      <cbc:ID schemeID="SAC">9983.11</cbc:ID><!--1-->
    </cac:AdditionalItemIdentification>
    <cac:CommodityClassification>
      <cbc:CommodityCode>S</cbc:CommodityCode><!--2-->
    </cac:CommodityClassification>
  </cac:Item>
</cac:InvoiceLine>
----
<1> Service Accounting Code with `schemeID="SAC"` (required for services, ibr-185-ae).
<2> Item type `S` (Services) via `cac:CommodityClassification/cbc:CommodityCode`. No `cbc:ItemClassificationCode` — services are not classified by HS.

==== VAT category, rate and exemption

UAE uses the EN/Peppol VAT category code set: `S` (Standard rated), `Z` (Zero rated), `E` (Exempt from VAT), `O` (Not subject to VAT), `AE` (Reverse charge) and `N` (Standard rate additional VAT).

* Standard rated (`S`) VAT rate MUST be exactly `5.00`.
* For category `E`, an exemption reason code MUST be present at the same level (line, document allowance/charge, or VAT breakdown) as the category code.
* For category `AE` (reverse charge), the buyer's VAT identifier MUST be present, the line's VAT amount MUST be zero, and the *Type of goods or services* code (BTAE-09) — taken from the UAE Goods/Services subject to RCM list — MUST be carried on `cac:CommodityClassification/cbc:NatureCode` for the line.

==== Profit Margin Scheme

Supplies under the UAE VAT Profit Margin Scheme (Article 43 of the UAE VAT Decree-Law) use VAT category code `N` (_Standard rate additional VAT_ — standard VAT calculated for an additional taxable base when the additional taxable base is not included in the document totals). Under the scheme, VAT is assessed on the supplier's profit margin and settled directly with the FTA; it is not charged to the buyer and the VAT *amount* on the invoice is always zero. The statutory rate (`5.00`) MUST nevertheless be provided in the `cbc:Percent` field.

The Profit Margin Scheme MUST be signalled with BTAE-02 position 3 set to `1` (e.g. `00100000`). This flag is required because the target format validates that every tax category uses code `N` when the margin-scheme bit is set.

*Example* +
_Profit Margin Scheme invoice — VAT amount 0, rate 5.00, BTAE-02 position 3 set_
[source,xml]
----
<Invoice>
  <!-- Code omitted for clarity -->
  <cbc:InvoiceTypeCode name="00100000">380</cbc:InvoiceTypeCode><!--1-->
  <!-- Code omitted for clarity -->
  <cac:TaxTotal>
    <cbc:TaxAmount currencyID="AED">0.00</cbc:TaxAmount>
    <cac:TaxSubtotal>
      <cbc:TaxableAmount currencyID="AED">45000.00</cbc:TaxableAmount>
      <cbc:TaxAmount currencyID="AED">0.00</cbc:TaxAmount>
      <cac:TaxCategory>
        <cbc:ID>N</cbc:ID><!--2-->
        <cbc:Percent>5.00</cbc:Percent><!--3-->
        <cac:TaxScheme>
          <cbc:ID>VAT</cbc:ID>
        </cac:TaxScheme>
      </cac:TaxCategory>
    </cac:TaxSubtotal>
  </cac:TaxTotal>
</Invoice>
----
<1> BTAE-02 transaction type code with position 3 = `1` (Profit Margin Scheme).
<2> Category code `N` for Profit Margin Scheme.
<3> The statutory rate `5.00` MUST be present; VAT is settled on the supplier's margin outside the invoice.

==== Reverse charge: standard item identifier

When the line is reverse-charged (category `AE`), the line MUST carry an *item standard identifier* (`cac:StandardItemIdentification/cbc:ID`) with `@schemeID = "0160"` (GS1 GTIN).

==== Free Trade Zone Beneficiary

In free-trade-zone supplies (BTAE-02 transaction type code matching the FTZ flag, `1XXXXXXX`), the *Beneficiary ID* (BTAE-01) — the TRN or TIN of the FTZ beneficiary — is carried using the existing `puf:RestrictedInformationParty` extension with `Key = 'Beneficiary'`.

The beneficiary has no VAT accounting role in the document, so its TRN is carried on `cac:PartyIdentification/cbc:ID` with `@schemeID = 'AE:TRN'`. A beneficiary that is not registered for VAT uses `@schemeID = 'AE:TIN'` instead. A `cbc:ID` without a scheme identifier is not processed and the Beneficiary ID will be missing from the resulting invoice.

*Example* +
[source,xml]
----
<Invoice>
  <ext:UBLExtensions>
    <ext:UBLExtension>
      <ext:ExtensionURI>urn:pagero:ExtensionComponent:1.0:PageroExtension:RestrictedInformationParty</ext:ExtensionURI>
      <ext:ExtensionContent>
        <puf:PageroExtension>
          <puf:RestrictedInformationParty>
            <puf:Key>Beneficiary</puf:Key><!--1-->
            <cac:Party>
              <cac:PartyIdentification>
                <cbc:ID schemeID="AE:TRN">100000000000003</cbc:ID><!--2-->
              </cac:PartyIdentification>
            </cac:Party>
          </puf:RestrictedInformationParty>
        </puf:PageroExtension>
      </ext:ExtensionContent>
    </ext:UBLExtension>
  </ext:UBLExtensions>
  <!-- Code omitted for clarity -->
</Invoice>
----
<1> `Key` set to `Beneficiary`.
<2> TRN of the free-trade-zone beneficiary. Use `@schemeID = "AE:TIN"` and the 10-digit TIN when the beneficiary is not registered for VAT.

==== Disclosed Agent Principle

In disclosed-agent billing (BTAE-02 transaction type code matching the disclosed-agent flag, `XXXXX1XX`), the *Principle ID* (BTAE-14) — the TRN of the principle — is carried using the same `puf:RestrictedInformationParty` extension with `Key = 'Principle'`. The Principle ID MUST be different from the Seller VAT identifier.

As for the Beneficiary above, the TRN is carried on `cac:PartyIdentification/cbc:ID` with `@schemeID = 'AE:TRN'`.

*Example* +
[source,xml]
----
<Invoice>
  <ext:UBLExtensions>

            <puf:Key>Principle</puf:Key><!--1-->

                <cbc:ID schemeID="AE:TRN">100000000000555</cbc:ID><!--2-->
              </cac:PartyIdentification>
            </cac:Party>
          </puf:RestrictedInformationParty>
        </puf:PageroExtension>
      </ext:ExtensionContent>
    </ext:UBLExtension>
  </ext:UBLExtensions>
  <!-- Code omitted for clarity -->

<1> `Key` set to `Principle`.
<2> TRN of the principle, different from the Seller VAT identifier.

==== Deemed Supply

Deemed supplies (BTAE-02 position 2 set to `1`, e.g. `01000000`) are supplies made without consideration — typically gifts or samples above the FTA de-minimis threshold.

* The buyer endpoint ID is always `9900000097` (scheme `0235`), whoever the buyer is (UAE Electronic Invoicing Guidelines V1.1, p.25). Pagero sets it, and any endpoint sent in PUF is replaced.
* A buyer TIN (`cac:PartyIdentification/cbc:ID` with `@schemeID = 'AE:TIN'`) or buyer TRN (`cac:PartyTaxScheme/cbc:CompanyID`) is still required, because the predefined endpoint is not a TIN (ibr-135-ae). No placeholder value is published for a deemed supply without a recipient.
* The payment due date (`cbc:DueDate`) and payment means are not required (ibr-127-ae, ibr-191-ae).

When no invoice is issued to a recipient, the document is only reported to the FTA and is not exchanged.

==== Exports

Export supplies (BTAE-02 position 8 set to `1`, e.g. `00000001`) are zero-rated supplies of goods or services delivered outside the UAE.

* When the buyer is not reached over Peppol, Pagero sets the buyer endpoint ID to the predefined value `9900000099` (scheme `0235`), so it does not need to be sent in PUF. A buyer that is reached over Peppol keeps its own Participant Identifier and scheme.
* A `cac:Delivery/cac:DeliveryLocation/cac:Address` with street name, city, country subdivision and country code MUST be present, unless the delivery country is `AE` (ibr-152-ae).
* The Incoterms code (BTAE-22) is optional. When `cac:DeliveryTerms` is sent, its `cbc:ID` MUST carry the Incoterms code (ibr-196-ae).
* The applicable VAT category is `Z` (zero rated) — `cbc:Percent = 0.00`.

The customs reference number (BTAE-21) is optional. It is provided as a customs declaration reference, see <<_customs_declaration_reference, Customs declaration reference>>: `cbc:ID` with `@schemeID = 'ED'` (export declaration), or `'ABT'` (import declaration) when the value is an import declaration. PINT AE has a single customs reference field with no declaration type and no date, so only one value reaches the target: the first `ED` reference, otherwise the first `ABT` reference. `cbc:IssueDate` is not used.

*Example* +
_Customs reference number on an export_
[source,xml]
----
<Invoice>
  <!-- Code omitted for clarity -->
  <cac:AdditionalDocumentReference>
    <cbc:ID schemeID="ED">EXP010101234</cbc:ID><!--1-->
  </cac:AdditionalDocumentReference>
  <!-- Code omitted for clarity -->
</Invoice>
----
<1> Customs reference number (BTAE-21), here an export declaration.

==== Credit note reason code

When the document is a credit note (`cbc:CreditNoteTypeCode` `381` or `81`, including a self-billed credit note), the credit note reason code (BTAE-03) MUST be provided. The supported values are `DL8.61.1.A` through `DL8.61.1.E` and `VD` (volume discount). See https://pagero.github.io/puf-code-lists/#_correction_reason_codes_for_united_arab_emirates[PUF-023-CORRECTIONCODE (United Arab Emirates)^] for the definition of each code.

The code is carried on `cac:BillingReference/cac:InvoiceDocumentReference` through the existing `puf:BillingReferenceExtension` (path `puf:BillingReferenceExtension/puf:Code`). When the reason code is `VD`, the credit note MUST NOT reference a preceding invoice. Peppol PINT AE rule ibr-055-ae rejects a `VD` credit note that has one, and requires the reference for every other reason code, although the PINT AE text describes it as optional for `VD`. Because PUF carries the code inside `cac:BillingReference`, send `cac:BillingReference` for `VD` only as the carrier of the code: leave `cbc:ID` empty and send no `cbc:IssueDate`.

*Example* +
_Volume discount credit note without a preceding invoice reference_
[source,xml]
----
<CreditNote>
  <!-- Code omitted for clarity -->
  <cbc:CreditNoteTypeCode name="00000000">381</cbc:CreditNoteTypeCode>
  <!-- Code omitted for clarity -->
  <cac:BillingReference>
    <cac:InvoiceDocumentReference>
      <ext:UBLExtensions>
        <ext:UBLExtension>
          <ext:ExtensionURI>urn:pagero:ExtensionComponent:1.0:PageroExtension:BillingReferenceExtension</ext:ExtensionURI>
          <ext:ExtensionContent>
            <puf:PageroExtension>
              <puf:BillingReferenceExtension>
                <puf:Code>VD</puf:Code><!--1-->
              </puf:BillingReferenceExtension>
            </puf:PageroExtension>
          </ext:ExtensionContent>
        </ext:UBLExtension>
      </ext:UBLExtensions>
      <cbc:ID/><!--2-->
    </cac:InvoiceDocumentReference>
  </cac:BillingReference>
  <!-- Code omitted for clarity -->
</CreditNote>
----
<1> Credit note reason code (BTAE-03) `VD`.
<2> Empty preceding document number, so no preceding invoice reference reaches the PINT AE document.

==== Out of scope of VAT and Credit-note related to goods or services

When the invoice type code is `480` (Out of scope of VAT) or `81` (Credit note related to goods or services), the buyer's legal registration identifier (IBT-047) is mandatory regardless of whether the buyer is VAT-registered, and all VAT category codes used on the document MUST be one of `E` / `O` / `Z`. The seller VAT identifier is *not* required in these cases.

==== Self-billing

In PUF, self-billing is *not* signalled through a dedicated UBL document type code. Self-billed documents keep their original type code (`cbc:InvoiceTypeCode = 380` for a self-billed tax invoice, `cbc:CreditNoteTypeCode = 381` for a self-billed credit note) and are flagged through the standard `puf:SelfBilled` extension at document level. See <<_self_billing_indicator, Self Billing Indicator>> for the structure.

*Example* +
_Self-billed UAE tax invoice_
[source,xml]
----
<Invoice>
  <ext:UBLExtensions>
    <ext:UBLExtension>
      <ext:ExtensionURI>urn:pagero:ExtensionComponent:1.0:PageroExtension:SelfBilled</ext:ExtensionURI>
      <ext:ExtensionContent>
        <puf:PageroExtension>
          <puf:SelfBilled>true</puf:SelfBilled><!--1-->
        </puf:PageroExtension>
      </ext:ExtensionContent>
    </ext:UBLExtension>
  </ext:UBLExtensions>
  <!-- Code omitted for clarity -->
  <cbc:InvoiceTypeCode name="00000000">380</cbc:InvoiceTypeCode><!--2-->
  <!-- Code omitted for clarity -->
</Invoice>
----
<1> Self-billing flagged through the `puf:SelfBilled` extension.
<2> Original tax-invoice type code `380` retained in PUF — UAE does not use a separate PUF self-billing type code.
